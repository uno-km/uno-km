# AMEVA 개발 표준 및 엔지니어링 거버넌스 규정
(AMEVA Strict Engineering Standards & Development Governance)

- **문서 식별자**: `AOSF-ENG-STD-2026-V1`
- **최초 제정일**: 2026-09-01
- **적용 대상**: AMEVA 생태계 전체 프로젝트 (Web, SDK, 온디바이스 모바일 런타임, AI 에이전트) 및 모든 기여 에이전트/엔지니어
- **준수 의무**: **절대 타협 불가 (Zero-Tolerance / Strict Enforcement)**

---

## 1. 에러 처리 및 자원 관리 절대 원칙 (No-Fallback & Strict Resource Deallocation)

### 1.1 "에러는 에러다 (An Error is an Error)"
아름답고 친절하게 포장된 거짓 성공은 시스템의 잠재적 파멸을 부릅니다. 에러를 감추거나 왜곡하지 마십시오.

1. **폴백(Fallback) 전면 금지**: 
   - 네트워크 실패, 모델 로드 실패, 연산 오류 발생 시 내부에서 임의의 더미 데이터나 임시 mock 객체로 대체하여 정상 작동하는 척 넘기는 행위를 일절 금지합니다.
2. **하드코딩(Hardcoding) 데이터 주입 금지**: 
   - 실제 연산 결과를 위장하는 임의의 상수값, 가짜 토큰, 고정된 더미 응답을 코드 내부에 은폐하지 마십시오.
3. **빈 에러 포획(Silent Exception Catching) 금지**: 
   - `except Exception: pass`, `catch(e) {}`와 같이 에러를 삼켜버리는 패턴은 적발 즉시 거부(Reject)됩니다.
4. **거짓 불리언/빈값 반환(`return True`, `return ""` 등) 금지**: 
   - 작업이 실패했음에도 상위 호출자에게 `True`, `""`, `[]`, `None` 등을 반환하여 에러가 발생하지 않은 것처럼 기만하지 마십시오.

### 1.2 예외 노출 및 우아한 자원 해제 (Fail-Fast & Clean Cleanup)
- **명확한 예외 표출**: 오류 발생 시 스택 트레이스, 발생 원인, 입력 파라미터를 명시한 정확한 예외(`Custom Domain Exception`)를 즉시 상위로 전파(Throw/Raise)하여 사용자와 호출자가 문제를 100% 인지할 수 있게 해야 합니다.
- **철저한 자원 해제 (RAII & Deallocation)**: 예외 발생으로 프로세스가 중단되더라도, 할당된 메모리(RAM/VRAM), 임시 캐시, 파일 핸들러, 소켓 디스크립터, GPU 버퍼는 `try-finally`, 컨텍스트 매니저(`with`), 소멸자(`RAII`)를 통해 100% 안전하게 즉시 해제해야 합니다.

## 2. 단계별 페이즈 분할 개발 및 사전 승인 프로토콜 (Phased Development & Pre-Approval)

절대로 전체 기능을 한 번에 독단적으로 개발하여 밀어붙이지 마십시오. 모든 작업은 명확한 Phase로 분할되어야 하며, 각 Phase 진입 전 **주인장(User)에게 사전 보고 후 승인**을 받아야 합니다.

### 2.1 사전 보고 시 필수 작성 항목 (100% 한국어)
사전 승인 요청 시 반드시 다음 5개 요소를 상세히 포함해야 합니다:

1. **구현 계획 및 조건**: 구체적으로 어떤 기술적 메커니즘과 제약 조건하에서 구현할 것인가.
2. **트레이드오프 (Trade-offs) 분석**: 이 설계를 채택함으로써 얻는 이점과 감수해야 하는 비용/한계점 명시.
3. **빅테크 레퍼런스 비교**: 동일한 문제를 빅테크(Google, Meta, Apple, Microsoft 등)는 어떤 아키텍처와 알고리즘으로 해결했는지 비교 분석.
4. **성능 및 지연시간 비교 표 (Benchmark Comparison Table)**: 메모리 점유율, 지연시간(ms), 바이너리 크기 등을 기존 솔루션 및 대안과 수치로 비교.
5. **대안(Alternatives) 검토**: 고려했던 대안 기술들과 그 대안을 채택하지 않은 명확한 엔지니어링 근거 제시.

## 3. 독단적 문제 규정 금지 (Zero-Assumption & Confirmation First)

- **임의 판단 절대 금지**: "저사양 기기이므로 가벼운 모델 A를 기본값으로 설정하자", "이 방식이 편하니 이렇게 구조를 바꾸자" 등 엔지니어가 스스로 문제를 지레짐작 규정하여 코드를 작성하는 행위를 전면 금지합니다.
- **사전 질의 의무**: 기본 모델 선정, 아키텍처 분기점, 파라미터 기본값, 외부 인터페이스 설계는 코드를 작성하기 전에 반드시 주인장에게 확인 질문을 드리고 명시적 컨펌을 득한 후 착수하십시오.

---

## 4. 실시간 동적 로깅 및 계측 가능한 정밀 테스트 (Live Dynamic Logging & Real Metrics)

- **단순 PASS/FAIL 날조 금지**: "테스트를 완료했고 성공했습니다"와 같은 정적인 한 줄 보고는 무효입니다.
- **동적 실행 로그 출력**: 테스트 및 런타임 실행 중 각 단계별 진행 상황, 실제 소요 시간(ms 단위 측정치), 사용된 모델명, 양자화 파라미터, 하드웨어 백엔드(Vulkan/NEON/WebGPU), 피크 RAM/VRAM 점유량이 실시간으로 출력되어야 합니다.
- **검증 가능성**: 테스트 코드는 누구나 동일한 환경에서 재현 가능하고 측정 가능(Measurable & Reproducible)하도록 작성되어야 합니다.

## 5. 객체지향 설계, 모듈화 및 선제적 리팩토링 (OOP, Modularity & Proactive Refactoring)

1. **단일 책임 원칙 (SRP) 및 추상화**: 모든 클래스와 모듈은 단 하나의 명확한 책임을 가지며, 하드웨어 계층과 비즈니스 로직은 명확한 인터페이스로 추상화 분리되어야 합니다.
2. **선제적 리팩토링 (Boy Scout Rule)**: 코드베이스 전반에서 유사한 패턴, 2회 이상 중복된 코드, 결합도가 높은 로직이 감지되는 즉시 리팩토링을 수행하여 코드 순도를 유지해야 합니다.
3. **확장성 확보**: 신규 하드웨어(NPU, 새로운 SoC), 신규 모델 아키텍처가 추가되더라도 기존 코드를 뜯어고치지 않고 플러그인 형태로 확장 가능하도록 설계하십시오.

## 6. 촘촘한 주석 및 인라인 문서화 (Extensive Comments as Insurance)

> *"주석의 용량은 우리와 후대 엔지니어가 짊어질 미래의 고난과 시련에 대한 보험금이다."*

1. **변수/상수 단위 주석**: 핵심 변수, 버퍼 크기, 임계값, 상태 플래그 선언 시 해당 변수의 물리적 단위(ms, bytes, tokens), 유효 범위, 목적을 명시하십시오.
2. **모듈 및 Import 주석**: 외부 라이브러리나 내부 모듈을 `import` / `#include`할 때 왜 이 모듈이 필요한지, 어떤 역할을 수행하는지 한 줄 주석을 병기하십시오.
3. **복잡한 수식 및 비트 연산**: SIMD 어셈블리, 비트 시프트, 텐서 인덱싱, 포인터 연산에는 수학적 원리와 메모리 레이아웃 구조를 다이어그램 수준으로 촘촘히 주석 처리하십시오.

## 7. 100% 원터치 설치 보장 (One-Touch Frictionless Installation)

사용자 및 개발자의 설치 경험은 무조건 원터치로 종결되어야 합니다.

1. **표준 패키지 매니저 단일 명령**:
   - Python: `pip install <package-name>`
   - Node.js: `npm install <package-name>`
2. **복합 툴체인 의존성 처리**:
   - 시스템 패키지나 NDK/C++ 라이브러리가 필요한 경우에도 사용자가 일일이 컴파일 명령어를 치게 하지 말고, 패키지 내부 사전 빌드 바이너리 휠(Wheel) 또는 단일 실행 쉘 스크립트(`install.sh` / `setup.py`)로 원터치 구동되도록 패키징하십시오.

## 8. 내부 `termux-` 생태계 라이브러리 연계 및 명세 준수 규칙

1. **공식 명세 정밀 확인 의무**: 
   - `termux-bitnet`, `termux-diffusion`, `termux-stt`, `termux-train`, `termux-aichain` 등 기존 내부 라이브러리를 연동할 때는 반드시 대상 프로젝트의 `doc.config.yaml`, API 레퍼런스, 타입 정의 명세를 먼저 정독하고 정확한 인터페이스로 호출하십시오.
2. **타 라이브러리 임의 수정 금지**: 
   - 연동 과정에서 기존 라이브러리의 코드 수정이나 인터페이스 변경이 필요한 경우, 임의로 손대지 말고 **반드시 주인장에게 원인과 수정 계획을 보고하고 승인을 받은 후** 진행하십시오.
3. **생태계 간 연계 기능 사전 승인**: 
   - 패키지 간의 복합 파이프라인(예: STT 음성인식 -> BitNet LLM 추론 -> TTS 음성합성 연계 에이전트)을 기획/개발할 때도 사전에 구조도와 함께 주인장의 승인을 득하십시오.

## 9. 규정 위반 시 조치
- 위 8대 원칙 중 단 하나라도 위반된 PR, 커밋, 생성 코드는 즉시 롤백 및 재작성 대상이 되며, 머지될 수 없습니다.
- 모든 엔지니어링 에이전트는 코드 작성 전 본 문서를 시스템 프롬프트 및 컨텍스트의 최상위 우선순위 지침으로 준수해야 합니다.
